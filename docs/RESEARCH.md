# Mock API landscape and implications for this project

Checked **2026-10-15**. This is research for the new project plan, not an implementation or a claim that the proposed features already exist. Both files in [old/](old/) were read and are preserved.

**Recommendation:** build an open-source front-end scenario toolkit with a useful public demo, reproducible local state, and test adapters. The strongest opportunity is reducing the effort required to test complete UI workflows. Delay controls, placeholder data, generated responses, and fault injection already have strong alternatives.

This comparison uses official documentation, maintainers' repositories, and an explicitly identified older first-party Platzi announcement. “Documented” means a capability is described in those sources; it does not mean its current hosted deployment was integration-tested. No competitor write requests, account creation, package installation, or load tests were performed. Pricing, quotas, licenses, and deployment behavior should be rechecked when choosing a dependency or service. A missing feature in the reviewed documentation is not proof that a product cannot provide it.

## 1. Compare the right kinds of tools

The market has several overlapping categories:

| Category | What it gives the developer | Important distinction |
|---|---|---|
| Public sample-data API | A URL with useful records immediately | A successful POST response may be simulated; a subsequent GET may not contain the new record. |
| Stateful fake backend | Data that changes across requests | State may be shared, per project, per process, or per test. These are different isolation guarantees. |
| In-process/browser interception | Mock behavior alongside application tests | This tests application handling without requiring a remote server, but does not exercise every browser/network transport behavior. |
| Service virtualization/proxy | Request matching, response sequences, faults, recording, verification | More setup than a canned dataset, but usually much deeper control over an existing API's behavior. |
| Contract-based mock | Responses generated or checked against a schema | Schema-valid mocks still do not prove that the real provider implements the contract. |
| Protocol/data utility | Status codes, echo, images, generated records | Useful building blocks; usually not a complete domain workflow. |

“Stateful” does not automatically mean disk persistence. “Seeded” does not automatically mean repeatable under concurrency. “Open source” does not automatically mean identical behavior on every hosting platform. These distinctions should be explicit in this project's documentation.

## 2. Ready-to-use sample APIs

| Service | Documented strengths and delivery | Writes, isolation, and reproducibility | Implication for this project |
|---|---|---|---|
| **JSONPlaceholder** | Public REST with six familiar resource families, filtering, nested relationships, and no signup/API key; [source available](https://github.com/typicode/jsonplaceholder). | Its guide explicitly says creates, updates, patches, and deletes are faked rather than saved. Stable public fixtures are useful for examples, but they do not support a create → refetch → edit workflow. [Official guide](https://jsonplaceholder.typicode.com/guide/). | Preserve the instant first-request experience. Clearly label simulated writes if offered; make real local state a separate, explicit mode. |
| **DummyJSON** | Rich REST datasets; search/sort/selection, limit/skip pagination, 0–5000 ms delay, auth/token flows, images, mock HTTP responses, and OpenAPI. Current navigation also includes TOTP, custom response, and webhook tools. [Docs](https://dummyjson.com/docs), [source](https://github.com/Ovi/DummyJSON). | Product create/update/delete are explicitly simulations. [Products documentation](https://dummyjson.com/docs/products). Do not treat a convenient hosted dataset as a pinned fixture version for CI. | This is the closest benchmark for breadth and low setup effort. Data + images + delay is already available together; differentiated value must go beyond that combination. |
| **ReqRes** | Hosted public demo and account-based APIs with collections, auth, and request logs. Its current homepage explicitly offers anonymous requests as well as API keys for accounts. | Anonymous demo is rate-limited and does not save data; account collections can persist between sessions. These are distinct product modes. [Official homepage](https://reqres.in/). | Compare demo with demo and private state with private state. Do not say ReqRes universally requires a key, or describe all its CRUD as fake. Account-level persistence still needs a test reset/isolation strategy. |
| **FakeStoreAPI** | Public e-commerce REST: products, carts, users, and login. Source and container-related files are published. | The README explicitly says posted data is not inserted into the database. Do not assume POST → GET persistence because CRUD-shaped routes exist. [Official repository](https://github.com/keikaavousi/fake-store-api). | Domain relationships are helpful; the project should add meaningful behavior such as inventory conflict and cart rollback instead of merely more resource names. |
| **Platzi Fake Store API** | First-party material describes e-commerce CRUD, pagination, JWT login, uploads/downloads, and API-client collections. [Platzi announcement](https://platzi.com/blog/la-api-para-nunca-parar-de-aprender-news/), [backend source](https://github.com/PlatziLabs/fake-api-backend). | The older announcement describes a mutable backend, but current persistence/reset guarantees and hosted isolation were not verified. Current documentation fetches failed during this research; see limitations below. | A valuable benchmark for complete application flows. The draft's current GraphQL and hosting claims require revalidation before a published comparison. Avoid using a shared mutable demo as a deterministic test fixture. |
| **GraphQLZero** | Zero-registration GraphQL queries, mutations, and relationships over the JSONPlaceholder dataset; source is published under MIT. [Official site](https://graphqlzero.almansi.me/), [repository](https://github.com/ealmansi/graphqlzero). | The reviewed site establishes its upstream dataset and mutation examples, not a private persistent test namespace. Mutation persistence was not exercised. | GraphQL sample data already exists. The opportunity is a shared REST/GraphQL scenario model, explicit mutation semantics, and field-level error cases. |

These tools remain sensible recommendations for a tutorial or a quick prototype. This project does not need to displace them to be useful.

## 3. Configurable mocking and test tools

| Tool | Documented strengths and delivery | State, determinism, and test implications | What to learn or integrate |
|---|---|---|---|
| **json-server** | Run a REST API from a JSON/JSON5 file; CRUD, filters, sorting, page pagination, and relations. Current main-branch docs warn that v1 is beta and describe changes from v0, including removal of the delay flag. [Repository/docs](https://github.com/typicode/json-server). | Developer-controlled data is much closer to real local CRUD than response-only public fakes. Separate data files/processes and reset fixtures are still needed for parallel suites. Pin a version; do not blend v0 and beta-v1 query syntax. | Support bring-your-own data later, with clear compatibility boundaries. “Local only” is an inaccurate limitation: a local HTTP server can be self-hosted. |
| **MSW** | Reusable network interception for browser and Node.js; REST, GraphQL, and WebSocket documentation; configurable delays and simulated network errors. [Introduction](https://mswjs.io/docs/), [delay](https://mswjs.io/docs/api/delay), [network errors](https://mswjs.io/docs/http/mocking-responses/network-errors). | Handlers can compute behavior and be reused; they need not be individually handwritten literal responses. The application/test owns fixture state and its lifecycle. Interception is a different execution surface from a deployed API. | Treat MSW as an adapter and complementary tool. Provide scenario factories with fresh state per test instead of requiring users to reimplement the domain model. |
| **Mirage JS** | Browser-oriented fake server with an in-memory database, ORM, relationships, factories, fixtures, and route shorthands. [Overview](https://miragejs.com/docs/getting-started/overview/), [models](https://miragejs.com/docs/main-concepts/models/), [factories](https://miragejs.com/docs/main-concepts/factories/). | Real stateful behavior exists inside the fake application's data layer. Fixtures and server lifecycle determine repeatability. Its browser focus is distinct from a server that other processes can call. | Learn from its relational fixture ergonomics and CRUD shorthands. A claim that mocking libraries always require every response to be written manually is false. |
| **Mockoon** | Local desktop configuration plus CLI/Docker self-hosting; dynamic templating, Faker helpers, latency, data buckets, and generated CRUD endpoints. [CRUD routes](https://mockoon.com/docs/latest/api-endpoints/crud-routes/), [templating](https://mockoon.com/docs/latest/templating/overview/), [CLI](https://mockoon.com/cli/). | CRUD routes mutate data buckets. The CLI exposes Faker seed configuration; seeded values still require disciplined state reset and request ordering. [CLI reference](https://github.com/mockoon/mockoon/blob/main/packages/cli/README.md). | A strong open-source competitor for custom API prototyping. Differentiate through ready-made UI scenarios, assertions, and consistent test lifecycle rather than “generated data” or “no response coding.” |
| **WireMock** | Open-source HTTP service virtualization with request matching, templating, record/playback, stateful scenarios, verification, and faults; separate cloud offering. [Documentation](https://wiremock.org/docs/), [stateful behavior](https://wiremock.org/docs/stateful-behaviour/). | Scenario transitions/reset support deterministic workflows. Fault support includes delays and connection/body failures; this is deeper than returning 500. [Fault documentation](https://wiremock.org/docs/simulating-faults/). Scope state carefully when sharing a server. | Use as a benchmark for failure sequences and request diagnostics; recommend it when deep protocol/service virtualization is the primary need. |
| **MockServer** | Standalone service virtualization, expectations, proxying, recording, OpenAPI-derived expectations, configurable delays/errors, and verification. [Expectation docs](https://www.mock-server.com/mock_server/creating_expectations.html), [OpenAPI](https://mock-server.com/mock_server/using_openapi.html). | Reset and selective clearing are part of its test lifecycle; request/response verification is documented. [Reset](https://www.mock-server.com/mock_server/clearing_and_resetting.html), [verification](https://mock-server.com/mock_server/verification.html). | Robust lifecycle and diagnostics are expected features for a test tool. Avoid claiming the proposed toolkit invents these capabilities. |
| **Prism** | OpenAPI-driven mock server with static/dynamic examples, request validation, and a validation proxy for a real upstream service. [Mocking guide](https://github.com/stoplightio/prism/blob/main/docs/guides/01-mocking.md), [proxy guide](https://github.com/stoplightio/prism/blob/main/docs/guides/03-validation-proxy.md). | Example/schema generation is not itself persistent domain state. Dynamic generation should not be assumed reproducible without an explicit fixture strategy. | Prefer interoperability with OpenAPI and examples over writing another complete schema-mocking engine initially. Explain the difference between a schema-valid response and a real stateful workflow. |
| **Mockttp** | Scriptable HTTP mock server/proxy with Node/browser test setup and HTTP/HTTPS support. [Repository](https://github.com/httptoolkit/mockttp), [setup](https://github.com/httptoolkit/mockttp/blob/main/docs/setup.md). | Server lifecycle can be managed around tests. Its API includes connection reset/close behaviors, including WebSocket rules. [WebSocket rule API](https://httptoolkit.github.io/mockttp/classes/WebSocketRuleBuilder.html). | An integration option for transport-level tests that cannot be reproduced faithfully by a Fetch `Response` or a public edge service. |
| **Beeceptor** | Hosted custom mocks with matching/templates, generated OpenAPI mocks, CRUD routes, and state primitives. [Rules](https://beeceptor.com/docs/create-mocking-server/), [OpenAPI](https://www.beeceptor.com/docs/oas-json-file-create-mock-server/). | Stateful data, counters/lists, and session/global storage are documented; a particular test must choose the correct scope and reset behavior. [State management](https://beeceptor.com/docs/mock-data-management/), [management API](https://beeceptor.com/docs/api/beeceptor-api/). | Hosted stateful mocking is already a mature alternative. Reproducible local/offline parity and a focused developer experience are stronger positioning than a broad feature checklist. |
| **MockAPI (mockapi.io)** | Hosted project/resource creation, generated REST routes, Faker-driven data, filtering, pagination, and relations. [Official quick start](https://github.com/mockapi-io/docs/wiki/Quick-start-guide). | Project data is editable and routes perform resource operations. Project separation is not automatically one isolated namespace per test. Exact reset/retention limits were not audited. | Make local fixture setup, reset, and import/export easier. Do not confuse this product with the separate `mockapi.com` service appearing in search results. |
| **Postman mocks** | Current v12 docs distinguish JavaScript mocks with dynamic/stateful logic, runnable locally or deployed, from cloud servers generated from collection examples. Collections can also use dynamic variables/templates. [Overview](https://learning.postman.com/docs/design-apis/mock-apis/overview/). | Saved examples and custom JavaScript are different modes. Delay, matching, and request logs are documented; isolation must be designed around the selected mode. [Calls](https://learning.postman.com/docs/design-apis/mock-apis/mock-server-calls/), [dynamic responses](https://learning.postman.com/latest-v-12/docs/design-apis/mock-apis/create-dynamic-responses). | Export useful collections and examples. Do not publish an outdated “Postman only returns static responses” comparison. |

This is a focused capability survey, not a ranking or an audit of every edition. Self-hosted open-source WireMock and WireMock Cloud, for example, should not have their features silently combined into one support promise.

## 4. Protocol, image, and data utilities

| Tool | What it already supplies | Product lesson |
|---|---|---|
| **httpbin** | HTTP request/response inspection, status responses, delays, streamed/dripped bodies, redirects, cookies, and other HTTP behavior. [Official endpoint reference](https://httpbin.org/legacy), [source](https://github.com/postmanlabs/httpbin). | Echo, redirect, cookie, cache, and content-type exercises belong in the roadmap. [Original repository](https://github.com/aaronpowell/httpstatus), [rebuild docs](https://http-stat.us/). | A 504 HTTP response is not the same failure as a client timeout, connection reset, or DNS failure. | **placehold.co** | Size/text/color/font placeholders, SVG and raster formats, retina sizes. [Official docs](https://placehold.co/). | A good baseline for simple image ergonomics. | **Lorem Picsum** | Photo placeholders, specific IDs, seeded selection, blur/grayscale, and image metadata. [Official docs](https://picsum.photos/). | Seeded photo selection already exists. Offline screenshot tests still need bundled/controlled assets and a clear image license policy. |
| **DiceBear** | Deterministic avatars via hosted API and libraries/CLI. Its core and individual art styles have distinct licensing considerations. [Official site and license links](https://www.dicebear.com/). | Consider integration or a small licensed bundled set rather than inventing an entire avatar system. Pin the style/version along with the seed. |
| **Faker** | Programmable synthetic data with seeds and explicit reference-date support. [Faker API](https://fakerjs.dev/api/faker), [date API](https://fakerjs.dev/api/date.html). | Keep versioned generated fixtures, seed, locale, and fixed reference time. A seed alone does not freeze dates or future generator changes. |
| **Mockaroo** | Schema-based data generation in multiple formats and configurable mock APIs that can use request parameters and simulate errors. [API docs](https://www.mockaroo.com/docs), [mock APIs](https://www.mockaroo.com/mock_apis). | The draft understates it as just a file generator. Import/export and small custom fixture packs offer value; implementing a full hosted schema editor can wait. |

The project should bundle the assets needed for its own offline examples. Depending on public image URLs would undermine the promised offline and deterministic test modes even if record JSON is fixed.

## 5. Adjacent testing tools: integrate rather than replace

**Playwright** provides browser network interception and HAR replay. Its documentation warns that service workers can intercept requests before Playwright's routing sees them. Plan distinct examples for (a) real browser → local server tests and (b) intercepted component/browser tests; do not stack MSW and Playwright routing without defining who owns each request. [Network documentation](https://playwright.dev/docs/network).

**Pact** addresses consumer/provider compatibility: consumer tests produce interactions and provider verification checks those interactions against a real implementation. A successful UI test against this proposed mock API cannot prove that an unrelated production backend satisfies its own contract. Provide examples of contract checking later; do not describe general mock scenarios as a replacement for provider verification. [How Pact works](https://docs.pact.io/getting_started/how_pact_works), [testing scope](https://docs.pact.io/getting_started/testing-scope).

For users testing their own API, OpenAPI import and contract examples are more valuable than another fixed `users` endpoint. For users learning front-end behavior, prebuilt scenarios and demo applications are more valuable than a large configurable virtualization platform. Supporting both should be phased deliberately.

## 6. Corrections to the existing draft

| Existing assumption | Research conclusion | Change to the new plan |
|---|---|---|
| Existing fake APIs are strong only at returning data. | Too broad. DummyJSON covers several useful UI behaviors; service-virtualization tools cover substantially deeper faults. | Position around convenience, curated workflow coverage, and reproducible test state. |
| MSW, Mockoon, Beeceptor, and MockServer require every response to be written manually. | Incorrect. Dynamic handlers, templating, factories/data buckets, CRUD generation, OpenAPI generation, and other reusable behaviors already exist. | Replace that comparison with setup effort, execution surface, and target workflow. |
| Combining data, delay, and images is sufficient differentiation. | DummyJSON already combines these. | Prioritize coherent scenario packs, actual state transitions, per-test lifecycle, and cross-adapter behavior. |
| ReqRes is uniformly behind an API key. | The current homepage distinguishes anonymous nonpersistent demo requests from account APIs with persistent collections. | Avoid a universal key requirement claim and volatile exact quotas. |
| `json-server` is local only. | It is a runnable server and can be self-hosted; the beta/stable distinction matters more. | Compare portability and setup honestly; pin any compatibility target. |
| Error simulation is a market gap because httpstat.us went down from abuse. | Fault simulation already has many providers. Fetch failure is not proof of permanent shutdown or its cause. The original maintainer documented abuse concerns historically, while the rebuild calls the original discontinued. [Maintainer fair-use issue](https://github.com/aaronpowell/httpstatus/issues/97), [rebuild](https://http-stat.us/). | Keep abuse controls for the project's own concrete resource risks; remove the outage-based market argument. |
| Fixed generated JSON alone makes tests deterministic. | It freezes reads, not clocks, IDs, response order, retries, random faults, mutable data, or image dependencies. | Version the whole fixture/scenario contract and inject/reset clock, IDs, counters, and randomness. |
| Stateless writes are enough until a late release. | They cannot validate create → refetch, delete → reload, optimistic rollback against durable state, or stale-write conflicts. | Put real isolated in-memory CRUD and reset into the first useful testing release. Disk persistence and public remote sandboxes are separate later decisions. |
| Any runtime can reproduce the same failure behavior. | Interception, local HTTP, edge HTTP, and browser security enforce different capabilities. The rebuild itself warns about buffering and transformed aborts. | State which scenarios are supported per adapter; test timing and cancellation through actual deployed transport. |
| The longest resource list gives the most useful product. | Deep reusable behaviors often cover more application work than another shallow dataset. | Start with a few relational domains; expand through versioned data packs. |

The draft already has good foundations: REST and GraphQL, consistent query semantics, error bodies, bounded delays, image metadata, typed contracts, local/self-hosted operation, and a playground. Preserve those goals while strengthening testability and avoiding claims of uniqueness that the sources do not support.

## 7. Highest-value gaps to turn into the roadmap

The following priorities are product recommendations inferred from the comparison, not claims that no competitor offers them.

1. **A deterministic scenario lifecycle.** Create/reset/dispose an isolated scenario; freeze or advance its clock; reproduce a failure by scenario version, fixture version, seed, and request/step identity. Ship an explicit fail → fail → succeed sequence before probabilistic chaos. Parallel tests must not consume each other's counters.
2. **Stateful workflows.** CRUD read-after-write, validation, conflict detection, optimistic updates, idempotent retries, delete semantics, and eventual-consistency scenarios. Start with in-memory state; distinguish restart persistence from session lifetime.
3. **A front-end behavior catalog.** Each scenario names the user-visible behavior to inspect: skeleton, stale content during refresh, empty result versus unavailable data, retry, rollback, refresh-token race, out-of-order search, failed next page, resumed stream, and broken image. Link behavior to a runnable example and an assertion recipe.
4. **Controlled data edge cases.** Null/absent/empty values, long strings, Unicode and RTL, duplicate labels, zero/negative/large numbers, DST and date boundaries, unavailable relations, and changing list contents. Keep deliberately invalid payloads separate from schema-valid fixtures.
5. **Test-specific delivery.** Plain HTTP for any language, a local server for browser/SSR integration, and MSW integration for fast isolated tests. Include strict unhandled-request behavior, useful mismatch diagnostics, and teardown that cancels delayed/streaming work.
6. **Auth and concurrency before exotic protocols.** Login/refresh/logout and separate permission failures are common application needs. Pair them with per-scenario state and a test clock. A signed demo token is not a security boundary for the host's management API.
7. **Streaming and files with explicit semantics.** SSE and NDJSON, reconnect/resume, partial or interrupted responses, upload validation, downloadable files, and cache/range exercises. Separate response delay, first-byte delay, chunk spacing, transfer rate, and client cancellation.
8. **Portable configuration and useful diagnostics.** Versioned import/export, JSON Schema/OpenAPI/GraphQL artifacts, request history with redaction, and a readable explanation of the rules applied to a response. A scenario URL should be shareable; secrets and arbitrary executable code should not be embedded in it.
9. **A truthful public mode.** Anonymous bounded demo traffic is valuable. CI examples should default to local isolated execution. Public mutable sandboxes need ownership, quotas, expiry, and cleanup; they should not be unlocked by a guessable session ID.
10. **Incremental extensibility.** Add custom schemas/data, specialist domain packs, webhooks, and broader protocols after the core lifecycle is reliable. WireMock, MockServer, Prism, and Mockttp remain good recommendations for needs outside the project's supported scope.

## 8. Evidence limits and checks before implementation

- **Version state:** the requested repository has drafts rather than an application manifest/lockfile. No installed framework versions were inferred. Dependency versions and runtime support are a separate implementation-readiness check.
- **Platzi:** the homepage and specific documentation URLs could not be retrieved by the research tool. Its [documentation repository](https://github.com/PlatziLabs/fake-api-docs) was marked archived on 2026-09-17. The [first-party announcement](https://platzi.com/blog/la-api-para-nunca-parar-de-aprender-news/) is dated 2022, so it supports historical feature context, not a current uptime, reset interval, or GraphQL compatibility guarantee. The Swagger page opened without readable specification content. Revalidate the live contract if using it in release comparisons.
- **httpstat.us:** retrieval failed; no uptime investigation was performed. The original repository and historical fair-use discussion support caution about abuse, not a verified diagnosis of today's availability.
- **Hosted capabilities:** the report did not inspect signed-in tiers or purchase plans. No exact prices or guaranteed service limits are carried over from third-party comparison posts.
- **Operational parity:** documented support for streaming, cookies, WebSockets, aborts, and CORS needs a real adapter/browser/deployment experiment. No benchmark or live transport test was run in this planning task.
- **Licensing and assets:** source availability was checked where linked, but this is not a full license/dependency audit. Before redistribution, inspect the exact dependency release and every bundled dataset/image/art-style license.
- **Ongoing maintenance:** recheck this comparison before public launch. Publish an “as checked” date and links; avoid “only,” “best,” or permanent feature-absence claims without reproducible evidence.
